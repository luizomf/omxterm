# One-time default Snippets

Current source attempts to install **Snippets0.1.0 enabled but dormant** for positively new **packaged** profiles on the existing optional targets: Linux ARM64/x64, macOS ARM64 and Windows ARM64. Windows x64 keeps built-in Snippets. This is not an update mechanism, existing-user consent, a new SDK or a claim that these new startup/package paths are qualified everywhere. Published0.24.0 behavior and historical failed checkpoints are unchanged.

## Enrollment and the permanent attempt

`src/main/default-snippets.ts` owns the policy; existing main captures synchronously as its first executable statement, before profile getters or startup writes. It uses actual `app.getName()` and `app.getPath('appData')` to derive the default userData, plus the account-home/XDG configuration and operational-state roots. It never observes freshness through userData/sessionData getters, which can create directories. Every root must be absolutely identified and absent, with no linked/non-directory/failed ancestor. Existing empty roots are existing profiles too. Development/default-app startup, readiness already reached, unsupported targets, `--user-data-dir`, uncertain identity and later actual-userData mismatch do not enroll.

At readiness, before the operational log, initial kit or package store, main compares actual userData and rederived name/config/state identity, and refuses existing product configuration, YAML, themes, extensions/state or logs that appeared since capture. Chromium may already have created the default root; after-ready directory contents are **not** a freshness heuristic or a Chromium-filename whitelist. One exclusive-created `<userData>/provisioning/default-snippets` file consumes the attempt, with literal `snippets-default-attempt-v1\n`. The filename/content are independent of package/host version, architecture and digest. A present, empty, corrupt, unknown or interrupted witness is never reset or retried. Directory/file sync is attempted before any publication; filesystem/Windows durability retains the ordinary store's limitations, not universal power-loss proof. This is a stable user-owned namespace, not defense against malicious same-user ancestor/mount replacement.

After `InstalledPackages.open`, before backend/manager composition and initial snapshot, the one-shot grant reads the bounded pinned resource and invokes ordinary `install(bytes,{expectedGeneration:0,enabled:true})`. Snapshot entries—including disabled installations and tombstones—win; production generation admission also rejects a concurrent change after a stale empty snapshot. Installation validates/extracts but never imports backend code. There is no startup network/catalog, extension view/backend activation, user YAML creation or shortcut reassignment.

Missing/corrupt resource, store failure or uncertain publication consumes the claimed attempt; terminal startup continues with existing runtime-unavailable handling or a fixed nonblocking startup warning. No private path/native diagnostic is logged by provisioning. Removing/disabling/collecting the package never removes the witness. Clearing only the installation store is not enrollment reset. Manual installation/reinstallation still uses ordinary explicit trust and activation. Deliberately deleting **all** profile/config/state history can create a new profile; this is not a machine-wide history ledger or automatic recovery.

## Fixed source input and reproducible packaging

The committed `assets/default-snippets/snippets-0.1.0.omxext` is the **unchanged public ZIP**, not a rebuild of current `extensions/snippets`. `assets/default-snippets.json` pins:

- 76,653 bytes; SHA256 `6c5723724d0dce26c589909405216c608dd071d7e9b04d63f733e012449c0ab7`;
- original source/tag commit `805e95dbc77552dc137707578b18b48ad6d047e9`;
- [immutable public archive](https://github.com/luizomf/omxterm/releases/download/ext-snippets-v0.1.0/snippets-0.1.0.omxext), with original host range `>=0.24.0-dev.8`, API `0.1.x` and semantic-input capability.

The ZIP contains its original license notices and package-owned `snippets.example.yaml`;
normal extraction retains that example inside the immutable version, never creates
or copies it to the user's `snippets.yaml`. Original release receipts remain `not-run`; retaining this input does not rewrite them. Host shared compatibility admits the current development family without changing that original manifest.

A normal locked checkout already has the fixed input. `npm run prepare:default-snippets` verifies it offline. To restore an absent/damaged checkout input, separately obtain that **exact URL**, then run `npm run prepare:default-snippets -- /absolute/path/to/snippets-0.1.0.omxext`; only exact hash/size bytes can replace the fixed source input. No acquisition occurs inside this command, build, package preparation or application startup. Do not rebuild/rename a different archive as0.1.0 or edit receipt qualification.

On an assigned build environment, run the normal locked setup/build/package command for its native target. Electron-builder's `beforePack` hook verifies the existing Linux launcher prerequisite and stages only the pinned input to `dist/default-snippets/<builder-os>-<arch>/bundled-snippets`. Target-specific stages prevent ARM64/x64 hooks from sharing or clearing each other's payload. Supported-target missing/corrupt input **fails packaging**, clearing stale staging first. Unsupported targets clear the stage and require no archive. Source build/development needs no preparation and opts out of provisioning even if this input exists.

The only external resource exception is `resources/bundled-snippets/snippets-0.1.0.omxext` (macOS `Contents/Resources/...`) for an optional target. Packaging filters copy that exact filename only; separate archive/receipt exclusions inside app.asar remain. Package verification checks target, exact directory contents, regular nonlinked file, byte count and SHA256 before its runtime probes; Windows x64 must have no bundled archive. Other `.omxext` archives/sidecars, lookalikes and an archive inside app.asar remain forbidden. This input is public data, readable by installed users, not a generated native binary.

## Evidence boundaries and remaining gates

One bounded pre-change Ubuntu26.04.1 ARM64 / Electron43.8.1 **source** diagnostic on `8169c2c` observed absent default roots before and after full product-module evaluation, then `Crashpad` before product readiness writes, with exact later-userData matching. It supports the simpler existing-main seam, not a different import graph or any packaged/other-platform promise. That disposable scope was exported/retired; it is not a replacement for earlier failed Ubuntu gates or A's separately held focus correction.

Local Node/filesystem regressions exercise actual public archive extraction, actual registry/generation admission, one-time/concurrent/failed claims, disable/tombstone/uninstall/collection/restart and narrow resource filters. Their deterministic lease adapter does **not** qualify kernel locks. Before target delivery, separately verify the changed startup graph and exact package: truly absent ordinary roots, **no user-data-dir override**, packaged identity/name/path, successful generation1 enabled+dormant publication, no backend/view/network/YAML, ordinary Quit/PTY/process/input settlement, restart, existing-profile preservation and deliberate disable/uninstall. Platform-native store locks, packaging/installer/deployment-floor and ordinary Snippets input/rendering qualification retain their own gates. Source delivery alone is not release or #741 closure.
