# OMXTerm 0.9.0

> Release candidate source preparation. The intended tag is `v0.9.0`. No tag,
> native artifact, exact checksum, native verification result, owner acceptance,
> GitHub Release, or publication is established by this document; those gates
> remain pending.

OMXTerm 0.9.0 adds optional Windows Default Shell selection through the existing
version 1 User Configuration. It also ships the public documentation maintenance
completed since the published 0.8.0 release.

## What is new

- **Optional `windowsShell` configuration.** A top-level `windowsShell` string
  selects the executable for future Default Shell sessions on Windows. OMXTerm
  uses the validated path exactly as written and starts it directly through the
  PTY with an empty argument vector. It does not construct a command string,
  add profiles or arguments, use a wrapper, identify the shell, expand syntax,
  or preflight a spawn.
- **Portable configuration structure with Windows-only effect.** Every Supported
  Platform accepts a non-empty `windowsShell` string without NUL. macOS and
  Linux perform no filesystem access, emit no warning, and continue using the
  operating-system-configured shell. Windows additionally requires an absolute
  Windows path and follows links or reparse points to require an existing
  regular-file final target. Inspection failure rejects the complete User
  Configuration; OMXTerm does not separately test ACL readability or
  executability.
- **Atomic reload ownership.** A successful `View -> Reload User Configuration`
  commits the selected Windows shell with the complete configuration. Every
  Default Shell session created afterward, including a new tab in an existing
  window, uses the latest committed selection. Existing sessions keep running
  unchanged. A rejected reload preserves the complete previous configuration
  and shell selection.
- **Per-session fallback titles.** A Default Shell session without an accepted
  OSC 0 or OSC 2 title displays the basename of the shell selected when that
  session started. Reloading from one configured shell to another therefore
  does not relabel an existing session; future sessions receive their own
  fallback.
- **Unchanged explicit-command and close behavior.** Startup
  `-e <program> [arguments...]` still takes precedence only for the first
  Terminal Tab and passes its executable and literal argv directly to the PTY.
  Later tabs and windows use the current Default Shell selection. ConPTY still
  cannot expose a foreground process name, so every live Windows session counts
  as Busy and asks before close when `confirmClose` is enabled.

## Changed-boundary verification plan

This map covers every material product, filesystem, packaging, version, or
public-documentation boundary changed since `v0.8.0`. It identifies current
automation but does not claim that an exact 0.9.0 native artifact has passed it.
Each later native record must bind results and remaining `UNVERIFIED` risk to the
exact source commit and artifact identity.

- Cross-platform `windowsShell` structure and Windows-only filesystem validation
  -> `windows-shell-configuration.test.ts` and `user-configuration.test.ts`
  cover strict keys, non-empty/NUL rejection on every platform, Windows absolute
  path requirements, no POSIX filesystem access, final-target inspection,
  regular-file acceptance, and complete fallback on error. `UNVERIFIED`
  (Windows ARM64): automation does not construct a real Windows reparse point or
  reproduce every host ACL and inspection failure; the risk is an exact host
  accepting or rejecting a linked or access-constrained executable differently
  from the injected filesystem seam.
- Windows Default Shell resolution and direct empty-argv PTY spawn ->
  `default-shell.test.ts` and `local-terminal-session.test.ts` cover current
  per-session resolution, exact path preservation, POSIX non-effect, empty argv,
  inherited Windows home, capability identity, and unchanged Windows Busy
  behavior. The real-ConPTY integration suite exercises configured Git for
  Windows Bash when `OMXTERM_WINDOWS_SHELL_TEST` identifies that installation.
  If that native seam is unavailable, the exact Windows record must mark
  alternate-shell ConPTY startup `UNVERIFIED` rather than infer a pass.
- Startup `-e` precedence -> launch-request, local-session, application
  lifecycle, and packaged-verifier tests cover one-time consumption, direct
  executable and literal argv delivery, Default Shell use by later sessions,
  failure behavior, packaged startup, and PTY readiness.
- Atomic reload ownership -> User Configuration loader and reloader tests cover
  one complete load, whole-state commit or rejection, preservation of the prior
  `windowsShell`, and serialized requests; Default Shell resolver tests cover
  reading the latest committed value for every future session. Existing-session
  lifecycle tests ensure configuration updates do not replace or write to a
  running PTY.
- Per-session fallback title -> local-session, terminal IPC controller, and
  Terminal Window title tests cover platform-correct basenames, association at
  session start, mixed-shell sessions, selection, OSC fallback, and final window
  fallback. `UNVERIFIED` (Windows ARM64): exact native tab and Window Chrome
  presentation after a shell-changing reload is visual UI behavior not observed
  by the automated seam; the risk is a stale or incorrectly displayed fallback
  despite the tested title state.
- WSL inherited-home behavior -> local-session tests cover passing the Windows
  account home unchanged as PTY `cwd`. `UNVERIFIED` (Windows ARM64 with WSL): no
  automated seam launches `wsl.exe` and observes the distribution-side working

  Linux distribution home.
- Final version, application reporting, and artifact names ->
  `release-version.test.ts`, `linux-package-assets.test.ts`, local PTY unit and
  integration tests, and packaged verification cover package and lockfile
  agreement, `TERM_PROGRAM_VERSION`, embedded application metadata, exact
  package and checksum names, and Linux helper `--version`. The later native

- Public documentation maintenance -> Prettier's formatting check and source
  diff review cover the maintained Markdown changes. This is documentation-only
  behavior and does not claim runtime or external-link availability.
- Unsigned package identity and platform trust UI -> macOS package verification
  must require a complete strict ad-hoc seal and reject a signing authority;
  Linux verification must reject an embedded AppImage signature; Windows
  packaging remains unsigned. `UNVERIFIED`: Gatekeeper presentation on macOS
  and SmartScreen presentation on Windows are automation-resistant security UI
  and are not inferred from package inspection.

The mandatory native commands remain `npm run check` on Apple Silicon macOS,

Their results are pending. Optional macOS dogfood or other observations are

## Supported Platforms

The Supported Platforms remain Apple Silicon macOS, Linux ARM64, and Windows
ARM64. The package formats remain DMG, AppImage plus its optional per-user
desktop helper, and NSIS respectively. x64, Intel macOS, and other
operating-system/architecture pairs are not supported by this candidate.

Every intended package carries no verified publisher identity. The macOS
application must receive a complete ad-hoc integrity seal during native
packaging, but it will have no Apple Developer ID signature and will not be
notarized. Native construction and verification of that seal are pending.

## Compatibility and migration

There are no incompatible schema changes and no manual file migration. Version
1 `config.json`, `snippets.json`, and Terminal Theme files accepted by 0.8.0
remain accepted unchanged. `windowsShell` is optional and keeps the User
Configuration schema at version 1.

Omitting `windowsShell` preserves the existing Windows selection order: Windows
PowerShell, then the ComSpec command processor. Existing macOS and Linux
configurations need no change. A shared configuration may include a Windows path
because macOS and Linux accept the string without interpreting it or changing
their Default Shell.

Users who opt in on Windows must provide an absolute executable path whose final
target is an existing regular file. OMXTerm does not migrate a shell name,
search `PATH`, expand a variable, or add shell-specific arguments. Startup `-e`
syntax and precedence are unchanged.

## Known limitations

- `windowsShell` selects one executable only and cannot supply arguments,
  profiles, environment expansion, shell syntax, or a wrapper command. Spawn
  permission and executable compatibility are reported only when the future
  session is actually started.
- `wsl.exe` inherits OMXTerm's Windows home as its Initial Working Directory.
  WSL commonly exposes it as `/mnt/c/Users/<user>` instead of starting in the
  Linux distribution's home; OMXTerm does not translate that directory.
- On Linux and Windows, BEL remains silent and marks the ringing session's
  title, but an unfocused Terminal Window does not request native platform
  attention ([#135](https://github.com/luizomf/omxterm/issues/135)).
- The Linux About panel still shows incomplete product metadata and a missing
  icon ([#134](https://github.com/luizomf/omxterm/issues/134)). The Terminal
  Window and installed desktop entry use the OMXTerm icon.
- Linux native Wayland rendering is not claimed; a Wayland session must provide
  XWayland. Normal AppImage execution requires kernel FUSE support, with
  `--appimage-extract-and-run` available as the fallback.
- On Windows, every live session counts as Busy because ConPTY does not expose
  the foreground process name. With `confirmClose` enabled, closing a live tab,
  window, or the application asks once. Electron 43 clipboard Paste can read
  only one Explorer file path; dropping multiple files remains complete and
  ordered.
- Tabs and Live Terminal Sessions remain ephemeral. Tab order is not saved, and
  tabs cannot move between windows. OMXTerm has no splits, saved or
  reconnectable sessions, Shell Integration, automatic updates, AI assistance,
  or built-in remote terminal features; tmux remains the session manager.

## Privacy and security

`windowsShell` is local configuration, not a trust decision. OMXTerm checks the
Windows path shape and final target described above, then starts the user-chosen
file with that user's ordinary operating-system permissions. Users remain
responsible for trusting the selected executable and its shell startup files.

Actionable User Configuration errors may show the configured path in the local
in-app surface and stderr. Operational Events still exclude configuration
contents, executable names, command arguments, environment contents, Terminal
Payload, clipboard data, titles, secrets, and transcripts. OMXTerm does not
upload configuration or logs and makes no telemetry, analytics, crash-report,
update-check, or remote-log network requests. Child shells and commands retain
the normal filesystem and network access of the user's account.
